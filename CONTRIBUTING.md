# Contributing to speedtest-go

This guide covers the tools, tasks, and conventions the project uses.

## Getting Started

### Cloning the Repository

```bash
git clone https://github.com/nicholas-fedor/speedtest-go.git
cd speedtest-go
```

## Building and Testing

Run the tasks from the repository root. `task` lists every task.

| Task | What it does |
| --- | --- |
| `task build` | Builds `bin/speedtest-go` with its version stamped |
| `task run -- <args>` | Runs the CLI with the given arguments, such as `task run -- --json` |
| `task test` | Runs the tests with the race detector and reports the total coverage |
| `task lint` | Runs golangci-lint and the betteralign struct alignment check |
| `task fmt` | Formats the code and aligns struct fields |
| `task modernize` | Fails when `go fix` modernizers would change the code. `task modernize FIX=true` applies them |
| `task vuln` | Reports known vulnerabilities in the dependencies |
| `task mocks` | Regenerates the mocks |
| `task check` | Runs `fmt`, `vet`, `modernize`, `test`, `lint`, and `vuln` in order |

## Packages and Images

| Task | What it builds |
| --- | --- |
| `task package` | Linux packages for amd64 in `dist/` with nfpm, as `.deb`, `.rpm`, `.apk`, and Arch Linux packages |
| `task package GOARCH=arm64 PACKAGERS=deb` | Packages for one architecture and the listed formats |
| `task release:snapshot` | Every release archive, package, SBOM, and Docker image, without signing or publishing |

`task clean` removes the build, test, and documentation site output.

## Documentation

The documentation site at <https://speedtest-go.nickfedor.com/> is built with [Hugo](https://gohugo.io/) and the [Hextra](https://imfing.github.io/hextra/) theme from `docs/`.

| Task | What it does |
| --- | --- |
| `task docs` | Regenerates the CLI reference in `docs/content/usage/cli-reference` from the command tree |
| `task docs:serve` | Previews the site with live reload |
| `task docs:build` | Builds the site into `docs/public` |
| `task docs:demo` | Records the CLI demo in `docs/static/images` with VHS, from the tapes in `docs/tapes` |

The demo runs a real speed test against speedtest.net, so recording it needs a network connection, and its numbers change between runs. Record it again after a change to the CLI's output.

The CLI reference is generated by `tools/docgen`, so edit the command and flag help in the code, not the generated pages. Run `task docs` after changing a command or a flag, and commit the regenerated pages. A test fails until the committed reference matches the code.

## Testing

Test files:

| Kind | File | Package |
| --- | --- | --- |
| Unit | `<file>_test.go`, beside each source file | The same package |
| Integration | `<pkg>_integration_test.go` | `<pkg>_test`, using only the exported API |
| Benchmark | `<file>_benchmark_test.go`, for hot paths only | The same package |
| Fuzz | `<pkg>_fuzz_test.go`, with `FuzzXxx` targets that `task fuzz` runs | The same package |

Conventions:

- Use [testify](https://github.com/stretchr/testify), with `require` for preconditions and `assert` for the rest.
- Call `t.Parallel()` in every test and subtest, unless it uses `t.Setenv` or package-level state.
- No test calls speedtest.net or any other external service. `internal/testserver` provides a fake speedtest.net API and speedtest server on the loopback interface.
- Mocks are generated by mockery into a `mocks` directory beside each interface. To mock a new interface, list it in `build/mockery/mockery.yaml` if its package is not already covered, then run `task mocks`.

## Branch Names

Branches are named `<type>/<short-kebab-description>`, such as `fix/upload-redirects`.

| Type | Use for | Example |
| --- | --- | --- |
| `feat` | A new feature of the library or the CLI | `feat/country-filter` |
| `fix` | A bug fix in the library or the CLI | `fix/upload-redirects` |
| `perf` | A performance improvement | `perf/fewer-allocations` |
| `refactor` | A code change that neither fixes a bug nor adds a feature | `refactor/cli-layout` |
| `test` | Adding or correcting tests | `test/fake-tcp-server` |
| `docs` | Documentation only | `docs/contributing` |
| `style` | Formatting with no change in behavior | `style/comment-wording` |
| `build` | The build, packaging, or release tooling | `build/taskfile` |
| `ci` | The GitHub Actions workflows | `ci/race-detector` |
| `chore` | Maintenance that fits no other type | `chore/betteralign` |
| `revert` | Reverting an earlier commit | `revert/country-filter` |

## Commit Messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), with the same types as branch names.

```text
<type>(<optional scope>): <subject>

<optional body>

<optional footer>
```

- Write the subject in the imperative mood, in lower case, without a trailing period.
- Mark a breaking change with `!` after the type and a `BREAKING CHANGE:` footer.

## Releases

Version metadata is stamped at build time by GoReleaser, and comes from Go's build information for `go install` and local builds, so the code never holds a version string.

1. Create a release branch with an empty commit, and open a pull request for it:

    ```bash
    git checkout -b release/vX.Y.Z
    git commit --allow-empty -m 'Release vX.Y.Z'
    git push origin release/vX.Y.Z
    ```

2. Merge the pull request.
3. Tag the merge and push the tag:

    ```bash
    git checkout master
    git pull origin master
    git tag vX.Y.Z
    git push origin vX.Y.Z
    ```

Pushing the tag starts the release workflow, which builds and publishes the archives, packages, and images.

## Pull Requests

- Keep each pull request to one change.
- Run `task check` before opening it.
- Use a Conventional Commits title, since pull requests are squashed and the title becomes the commit subject.
